# 複数エージェントの分担ルール

このリポジトリは複数の Claude セッション（別アカウント・別マシンを含む）が同時に触る。
新しい仕組みは足さない。**GitHub の Issue にある機能（ラベル・コメント・Assignee）だけ**で衝突を避ける。

## 1. 着手する前に Issue に宣言を 1 本書く

コードを触る前に、対象 Issue へこの 5 行をコメントする。書式は固定にして、機械にも人にも拾えるようにする。

```
**着手** <セッション名>
- 環境: <Unity 起動可否 / Blender 起動可否 / OS>
- 触る範囲: <ファイル・ディレクトリ>
- ブランチ: <branch 名>
- 検証できること / できないこと: <実機撮影は無理、など>
```

「環境」と「検証できないこと」を必ず書く。Unity を起動できないセッションが見た目の Issue を
「完了」と言ってしまう事故を、宣言の時点で防ぐのが目的。

## 2. 同時にラベルを付ける

| ラベル | 意味 |
|--------|------|
| `外部Claude対応中` | 主セッション（#71 のロードマップを回している Claude。`dev/*` も `wf/*` も使う）以外のエージェントが着手中 |

- 着手コメントとラベルは**必ず同時**に付ける。ラベルだけ / コメントだけは無効とみなす。
- **作業が終わったら（PR マージ・中断のどちらでも）自分で外す。** 外し忘れた札は「放置」であって「作業中」ではない。
- 誰が持っているかはラベルではなく**着手コメントの `<セッション名>`** で判別する。ラベルは「主セッション以外が触っている」という信号だけを持つ。

## 3. 札が付いている Issue は他のエージェントは触らない

触りたいときは奪わず、その Issue にコメントで聞く。返事が無いまま 24 時間過ぎたら、
「引き取ります」と 1 行書いてから引き取ってよい。

## 4. 触る範囲を宣言に書いて衝突を防ぐ

Issue の番号ではなく**ファイルの範囲**が衝突の単位。#71 が決めている担当分けと同じ考え方で、
宣言の「触る範囲」に書いたパスの外は触らない。範囲を広げたくなったら宣言を編集して追記する。

よく衝突する場所:

- `unity/KatsushikaCampusDays/Assets/Scripts/Editor/MaterialLibrary.cs` — 見た目の Issue がほぼ全部ここを通る
- `unity/KatsushikaCampusDays/Assets/Shaders/KCD_Toon.shader`
- `blender/kcd_lib/mats.py` — 上 2 つと色の定義が対になっている
- `README.md` / `docs/CREDITS.md`

## 5. ブランチと PR

- ブランチ名は `dev/<セッション名>` か `wf/<話題>`。`main` へ直接 push しない。
- PR 本文に `Closes #<番号>` と、**実機で確かめたこと / 確かめていないこと**を分けて書く。
- 確かめていない変更を含む PR は、タイトルの末尾に `(未検証)` を付けて、検証できるセッションへ渡す。

## 6. 進行中の作業を見つける方法

Issue のラベルだけでは、まだ宣言していない作業を取りこぼす。着手前に一度見る:

```bash
gh issue list --label 外部Claude対応中                  # 札の付いた Issue
git fetch origin && git branch -r --no-merged origin/main   # main に入っていない dev/* wf/*
gh pr list --state open
```

`wf/*` には、PR も札も無いまま main に入っていない作業が載っていることがある。Issue だけ見ると
空いて見えるので、ブランチ名の話題と Issue を突き合わせてから着手する。
