# スマホ・タブレット対応の設計（#187）

Web 版（WebGL）をスマホとタブレットのブラウザでも遊べるようにする。ネイティブアプリ（Android / iOS のビルド）は作らず、
GitHub Pages の 1 つのページを PC と共用する。

## 1. 着手前の状態

| 項目 | 状態 |
|------|------|
| 入力 | `KCDInput` がキーボード・マウス・ゲームパッドだけを読む。タッチを読むコードは 0 件 |
| メニュー | タイトル・キャラ選択・ポーズ・設定・クエストログ・リザルト・クレジットは、TMP の 1 枚の文字に選択肢を並べ、←→↑↓ と Enter で選ぶ。ボタン（`Selectable`）もタップの受け口（`IPointer*Handler`）も無い |
| 視点 | マウスの移動量。キャンパスに入るとポインタをロックする |
| 画面 | `CanvasScaler` は 1920×1080 を基準に幅と高さを半々で合わせる（`UIKit.Reference`）。文字は基準で 24〜32 px |
| ページ | 指だけの端末では読み込む前に「PC 向けのゲームです」を出し、「それでも読み込む」を待つ（#73） |
| 描画 | `createUnityInstance` に `devicePixelRatio` を渡していないので、端末の DPR のまま描く。画質の既定は Web 版で Medium |
| テクスチャ | WebGL の既定（DXT）。スマホの GPU は DXT を扱えず、Unity が RGBA32 に展開する（`WEBGL_BUDGET.md` 2.1。2048² で 1 枚 21.3 MiB） |

## 2. 方針

1. **ゲームのコードは `KCDInput` だけを見る**、という今の形を崩さない。タッチは `KCDInput` の入力元を 1 つ増やすだけにし、
   プレイヤー・会話・メニューの判定（`SubmitPressed` など）には手を入れない。
2. **タッチの操作 UI を出すかどうかは、最後に使った入力で決める。** 端末の種類では決めない。
   キーボード付きのタブレットや、タッチ画面の PC があるため。起動直後だけは、`Application.isMobilePlatform` と
   「マウスが無くタッチ画面がある」ことから決める。
3. **端末の制約（メモリ・GPU・通信量）に合わせる部分は、ページ（JavaScript）で読み込む前に決める。**
   テクスチャの形式と描く解像度は、Unity が動き出してからでは変えられないため。
4. 段階ごとに PR を分け、各段階の終わりで PC の遊び方が変わっていないことを確かめる。

## 3. 入力

### 3.1 入力元の組み立て

| 操作 | 作り方 | `KCDInput` 側 |
|------|--------|---------------|
| 移動 | 画面の左半分に指を置いたところに出るスティック。Input System の `OnScreenStick`（`ExactPositionWithDynamicOrigin`）で、仮想のゲームパッドの左スティックに書く | 今の `Gamepad.current.leftStick` の読み取りがそのまま効く |
| ジャンプ・調べる・ポーズ・クエストログ・写真 | `OnScreenButton` で仮想のゲームパッドの各ボタン（南・西・スタート・セレクト・北）に書く | 今のゲームパッドの読み取りがそのまま効く |
| 走る | 切り替えのボタン。押すと走り続け、スティックを離すと歩きに戻る | `Sprint` にタッチの切り替えの状態を足す |
| 視点 | スティックとボタンの外を指でなぞる。なぞった量（画面の高さに対する割合）を角度にする | `Look` にタッチの量を足す |
| ズーム | 2 本指で広げる・つまむ | `Zoom` にタッチの量を足す |
| 会話を進める | 会話の枠のどこを叩いても進む | `InteractPressed` / `SubmitPressed` にタッチを足す |
| メニュー | 選択肢の文字そのものを叩く（3.3） | 選んだ番号を各メニューに渡し、そのフレームの決定として扱う |

ボタンと移動を仮想のゲームパッドに書くのは、Input System が入力の更新の中で状態を書き換えるので、
`wasPressedThisFrame` がキーボードと同じ時刻・同じ意味で立つため。UI のイベント（`EventSystem.Update`）で
フラグを立てる作りにすると、そのフレームの `Update` が先に走ったスクリプトには 1 フレーム遅れて届き、
押した瞬間の判定（`JumpPressed` など）を取りこぼす。

視点となぞりは量なので、取りこぼしても 1 フレーム遅れるだけで済む。UI のイベントでためておき、
フレームの頭（実行順の早いコンポーネント）で 1 フレーム分として確定させてから `Look` が返す。

### 3.2 タッチとマウスの取り違え

ブラウザは指で叩くと、互換のためにマウスのイベントも出す。タッチの操作 UI を出している間は
`Look` と `Zoom` でマウスの移動量とホイールを読まない（叩いた位置へカメラが跳ぶのを防ぐ）。
ポインタのロックも掛けない。

### 3.3 メニューを叩いて選ぶ

メニューは TMP の文字に選択肢を並べているので、選択肢の文字に `<link="choice:N">` を付け、
叩いた位置の link を `TMP_TextUtilities.FindIntersectingLink` で引く小さな部品を 1 つ作り、
各メニューは「N 番を選んで決定した」を受け取るだけにする。

- 1 回目のタップで選び、同じものをもう 1 回叩いて決定する、にはしない。選択肢は 2〜5 個で、
  取り消しの効かない操作（はじめから・タイトルへ戻る）には今も確認の段がある。
- キーボードの ←→↑↓ と Enter はそのまま使える。

### 3.4 押せる大きさ

ボタンは画面の短辺の 13% 以上にする。6.1 インチの iPhone（短辺 6.5 cm）で約 8.4 mm になり、
Apple の 44 pt（同じ端末で約 7.3 mm）、Android の 48 dp（約 7.6 mm）の目安を満たす。

## 4. 画面

| 項目 | 方針 |
|------|------|
| 向き | 横向きだけ。縦に持っているときはページで「横向きにしてください」を被せる。ブラウザから向きを固定する方法は、Android の全画面のときにしか使えないため |
| 安全領域 | ページの CSS で `env(safe-area-inset-*)` の分だけキャンバスを内側に寄せる。ノッチと角の丸みに UI がかからない |
| 高さ | iPhone の Safari はアドレスバーの分だけ見える高さが変わる。`100vh` ではなく `100dvh` で合わせる |
| UI の大きさ | タッチの操作 UI を出している間は `CanvasScaler` の基準を 1280×720 にする（1.5 倍）。横持ちの 844×390（CSS px）では、会話の 32 px の文字が CSS で約 13 px から約 19 px になる |
| 全画面 | Android の Chrome は全画面のボタンを出す。iPhone の Safari は要素の全画面が使えないので出さない |

UI を 1.5 倍にすると、1920×1080 で余裕のない並び（クエストの追跡、ミニマップ、時計）がはみ出す。
はみ出す部品はタッチのときだけ位置と大きさを変える。

## 5. 重さとメモリ

| 項目 | 方針 |
|------|------|
| 描く解像度 | スマホは `devicePixelRatio` を 1.5 までにして `createUnityInstance` に渡す。DPR 3 のままだと描く画素が 4 倍になる |
| 画質の既定 | スマホは Low（`QualityTiers.DefaultFor`）。設定で上げられる |
| テクスチャ | ASTC で 2 本目のビルドを作り、ページが `WEBGL_compressed_texture_astc` の有無で読み込む方を選ぶ（Unity の手引きの「複数のテクスチャ形式でビルドする」）。配信の容量は 2 倍近くになるので `deploy_pages.py` の上限を見直す |
| 通信量 | 読み込む前の案内は残し、「PC 向け」ではなく通信量（数十 MB）の注意にする |

## 6. 段階

| 段 | 中身 | 終わりの条件 |
|----|------|-------------|
| 1 | 入力の土台（`KCDInput` のタッチの入力元、最後に使った入力の判定）と、キャンパスの操作 UI（スティック・視点・ジャンプ・走る・調べる・ポーズ）。会話を叩いて進める。タイトルとキャラ選択を叩いて選ぶ | スマホの画面のエミュレーションで、タイトルからキャンパスに入り、歩いて人に話しかけられる |
| 2 | 残りのメニュー（ポーズ・設定・クエストログ・リザルト・クレジット・写真モード・エンディング）を叩いて選ぶ | どの画面からも指だけで抜けられる |
| 3 | 画面（向き・安全領域・UI の大きさ・はみ出しの手直し） | 横持ちの小さい画面（844×390）で文字が読め、UI が重ならない |
| 4 | 重さとメモリ（DPR の上限・画質の既定・ASTC のビルド）。#73 の案内を通信量の注意に替える | 通信量と描く画素数を見積もり直し、`WEBGL_BUDGET.md` に書く |

1 段目は済み。リザルトも 1 段目で叩いて選べるようにした（キャンパスで一日が終わると、そこから指だけで抜けられないと遊びが止まるため）。

## 7. 確かめ方

- Unity の EditMode: 入力の計算（スティックの量、なぞりの量から角度、走るの切り替え、link の番号）を純粋な関数にして確かめる。
- Unity の PlayMode: Input System の `InputTestFixture` で仮想の `Touchscreen` を作り、指を置いて動かしたときに `KCDInput.Move` と `Look` が動くことを確かめる。
- ブラウザ: Playwright のスマホのエミュレーション（`has_touch`、`is_mobile`、844×390、DPR 3）と CDP の `Input.dispatchTouchEvent` で、タイトルからキャンパスに入り、スティックで歩けることを確かめる（音は消す）。
- 実機: iPhone の Safari と Android の Chrome での手触り・発熱・メモリの上限は、ここでは確かめられない。各段の PR に「実機で見てほしいこと」を書く。
